# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс: `/api/v1`

| Метод | Маршрут | Описание |
|---|---|---|
| `POST` | `/api/v1/tasks` | Создать задачу |
| `GET` | `/api/v1/tasks` | Список задач |
| `GET` | `/api/v1/tasks/{id}` | Получить задачу |
| `PUT` | `/api/v1/tasks/{id}` | Обновить задачу |
| `DELETE` | `/api/v1/tasks/{id}` | Удалить задачу |
| `GET` | `/api/v1/tasks/{id}/occurrences` | Даты выполнения задачи |

## Периодичность задач

### Получение дат выполнения

```
GET /api/v1/tasks/{id}/occurrences?from=2025-07-01&to=2025-07-31
```

Возвращает список дат в формате `YYYY-MM-DD`, на которые задача должна выполняться в указанном диапазоне.

Пример ответа:
```json
["2025-07-01", "2025-07-03", "2025-07-05"]
```

### Типы периодичности

| type | обязательные поля | описание |
|---|---|---|
| `daily` | `start_at`, `interval` | каждые N дней начиная с `start_at` |
| `monthly` | `month_days` | в указанные числа каждого месяца (1–30) |
| `specific_dates` | `dates` | только в указанные даты |
| `parity` | `parity` | только чётные (`even`) или нечётные (`odd`) числа месяца |

### Примеры запросов

**Ежедневная — каждые 2 дня:**
```json
{
  "title": "Обзвон пациентов",
  "status": "new",
  "recurrence": {
    "type": "daily",
    "start_at": "2025-07-01",
    "interval": 2
  }
}
```

**Ежемесячная — 1-го и 15-го:**
```json
{
  "title": "Формирование отчётности",
  "status": "new",
  "recurrence": {
    "type": "monthly",
    "month_days": [1, 15]
  }
}
```

**Чётные дни месяца:**
```json
{
  "title": "Инвентаризация",
  "status": "new",
  "recurrence": {
    "type": "parity",
    "parity": "even"
  }
}
```

**Конкретные даты:**
```json
{
  "title": "Плановый осмотр",
  "status": "new",
  "recurrence": {
    "type": "specific_dates",
    "dates": ["2025-07-10", "2025-07-20"]
  }
}
```

### Принятые решения и предположения

**Периодичность хранится внутри задачи (JSONB), а не в отдельной таблице.**
Периодичность неотделима от задачи — нет смысла в отдельном JOIN. JSONB позволяет хранить разные типы с разными полями без усложнения схемы.

**Задачи не создаются автоматически по расписанию.**
Сервис возвращает список дат через `/occurrences` — клиент или фоновый воркер сам решает, что с ними делать. Это сохраняет сервис stateless и не требует cron-воркера.

**`PUT /api/v1/tasks/{id}` обновляет периодичность целиком.**
Передача `recurrence: null` убирает периодичность. Отдельный endpoint для управления периодичностью не вводился — это соответствует существующей архитектуре, где PUT заменяет всю задачу.

**Даты в API передаются как строки формата `YYYY-MM-DD`.**
Это удобнее для клиента, чем `time.Time` с timezone. Внутри сервиса всё хранится в UTC.

**`start_at` обязателен только для типа `daily`.**
Для остальных типов точка отсчёта не нужна — `monthly`, `parity` и `specific_dates` не зависят от начальной даты.

**Числа месяца для `monthly` ограничены диапазоном 1–30.**
31-е число есть не в каждом месяце, поэтому верхняя граница — 30, чтобы задача выполнялась предсказуемо каждый месяц.
